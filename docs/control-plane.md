# 통합 제어 평면 (Control Plane)

대시보드 홈(`/`)의 **Command Center**가 보여주는 것. 이전에는 알트 스캐너·증권
오피스·진화 스쿼드·파이프라인 신호가 **각자** 페이퍼 장부를 회전시켰다. 네 개가
따로 놀면 마지막에 실행된 엔진이 앞 엔진의 결정을 그냥 덮어썼고, 어느 엔진이
돈을 벌었는지 알 길이 없었다. 이제 엔진은 장부를 건드리지 못한다.

```
소스(Upbit·Yahoo·RSS) → 파이프라인(HMM 국면·GARCH·신호 DAG)
   → 엔진 4개 ── 제안(proposal) ──▶ 중재기(arbiter) ──▶ 승인/오토파일럿 ──▶ 페이퍼 장부
```

코드: `backend/src/control/plane.ts` (단일 `controlPlane`), 상태 파일
`data/control/state.json`, 화면 `frontend/components/dashboard/command-center.tsx`.

## 제안 (proposal)

각 엔진은 `controlPlane.propose({ engine, targets, confidence, evidence, ref })`
한 가지만 호출한다. `targets`는 `{ market, weightPct }[]`, `confidence`는 0~1.

| 엔진 | 언제 | 확신도 |
|---|---|---|
| `office` 증권 오피스 | Handsel 오피스 런이 채점을 통과해 결정 JSON을 냈을 때 | 통과 단계 ÷ 전체 단계 |
| `evolution` 진화 스쿼드 | 세대마다 (`EVOLUTION_PROPOSE=true`) 또는 `POST /evolution/deploy` | 0.25 + 평균 적합도 ÷ 4 |
| `signals` 파이프라인 신호 | 15분마다 크립토 파이프라인 스냅샷 | 앙상블 알파의 평균 신뢰도 |

엔진당 살아있는 제안은 **하나**(새 제안이 이전 것을 대체), 유효기간
`proposalTtlH`(기본 30h). 만료된 제안은 중재에서 빠진다.

## 투자 유니버스 — 알트코인은 별개 도구가 아니라 자산이다

`backend/src/crypto/universe.ts`. 유니버스 = 메이저(BTC·ETH·XRP·SOL·DOGE) ∪ 24h 거래대금
상위 30 KRW 마켓 ∪ 현재 보유분. 30분마다 스캔(공유 캔들 저장소)에서 갱신된다. 데스크는
이 목록 전체의 시세·호가를 받아 파이프라인(신호 엔진)과 뉴스 감성에 넣고, 진화·오피스는
같은 스캔 시리즈를 쓴다. 그래서 알트는 **모든 엔진**의 거래 대상이다. 옛 "알트 스캐너"
엔진은 없어졌고 그 랭킹(모멘텀/변동성·HMM·GARCH)은 `/scanner`("투자 유니버스") 페이지의
자산 특성으로만 남는다. `GET /crypto/universe`.

## 협의회 (council) — 매니저들이 협의해서 최종 결정한다

가중평균 중재기는 없어졌다. 대시보드 기능마다 **총괄 매니저 에이전트** 하나가 있고
(`backend/src/control/council.ts`, 순수 함수), 결정은 그들의 협의록에서 나온다.

| 매니저 | 역할 | 입장의 근거 |
|---|---|---|
| 증권 오피스 총괄 | 제안 | 9역할 협의의 위원장 결정 |
| 진화 총괄 | 제안 | 본 적 없는 60일 시험을 살아남은 스쿼드 타깃 |
| 파이프라인 신호 총괄 | 제안 | 앙상블 알파 — **혼자서는 매수를 통과시킬 수 없다** |
| 센티먼트 총괄 | 지지·반대 | 실제 헤드라인 감성: BEARISH면 반대, BULLISH면 지지(+10% 기울기) |
| 리스크 총괄 | 거부권 | 킬스위치, 페이퍼 드로다운(≥8% 총노출 절반, ≥15% 전면 거부), 종목 상한·총노출·현금 하한 |

세 라운드:

1. **입장 표명** — 제안 매니저는 시장별로 SUPPORT(비중·확신도·근거) 또는 ABSTAIN,
   센티먼트는 감성으로 SUPPORT/OPPOSE/ABSTAIN, 리스크는 드로다운·킬스위치로 VETO.
2. **반대에 대한 수정** — 반대를 받은 지지자는 다른 제안 매니저가 함께 지지하면
   비중을 절반으로 물러서고, 혼자면 철회한다. 거부권이 있으면 전원 철회.
3. **표결 · 리스크 집행** — 서로 다른 제안 매니저 **2명 이상**이 지지한 시장만
   채택(정족수). 센티먼트 지지는 정족수에 안 들어간다. 채택 비중 = 지지자들의
   standing(엔진 가중치, 매일 실현수익으로 자동 갱신) 가중 평균 × (0.6 + 0.4 × 합의
   비율). 그 뒤 리스크 총괄이 한도를 집행한다 — 한도는 협의 대상이 아니다.

정족수를 채운 시장이 없고 장부가 이미 현금이면 결정은 `skipped`다. 협의록
(`decision.council`: rounds·tally·summary)은 결정에 그대로 남고 홈의 결정 카드에서
펼쳐 볼 수 있다.

## 중재 (arbiter) — 협의회 이전의 규칙 (참고)

살아있는 제안을 켜진 엔진끼리 섞는다.

1. 엔진 기여도 = `weight × (0.25 + 0.75 × confidence)`, 합이 1이 되게 정규화.
2. 종목 비중 = Σ 기여도 × 그 엔진의 목표 비중.
3. 제약(policy) 적용, 발동한 것은 결정의 `constraints`에 그대로 적힌다:
   `maxWeightPct`(종목당 상한) · `maxPositions`(상위 N만) · `grossMaxPct`(총노출)
   · `cashFloorPct`(현금 하한).
4. 회전율 = 현재 보유 비중 대비 절대 변화 ÷ 2. `minTurnoverPct` 미만이면
   **skipped**(거래할 가치가 없음).
5. 킬스위치가 켜져 있으면 **blocked**.
6. 마지막 집행 후 `minIntervalMin`이 안 지났으면 **pending**으로 붙잡아 둔다.
7. 오토파일럿이면 즉시 집행, 아니면 **pending** — 운영자가 승인/거부한다.

결정(`Decision`)에는 기여한 엔진과 가중치, 근거 줄(`rationale`), 발동한 제약,
회전율, 집행 결과(주문 수·건너뛴 종목·오류)가 남는다. 최근 200건을 보관한다.

## 집행 — 돈 경계는 그대로

집행은 `cryptoDesk.rotateTo()` 하나뿐이고 이것은 **페이퍼 전용**이다.
`CRYPTO_TRADE_ALLOW_REAL`이 켜진 실주문 모드에서는 rotateTo가 거부하므로 제어
평면이 실제 돈을 움직일 길이 없다. 데스크가 추적하지 않는 알트의 현재가는 집행
직전에 Upbit 티커로 채우고, 그래도 없는 종목은 건너뛰고 `skipped`에 남긴다.

## 귀속 (attribution) — 5분 마크, 결정 단위 타율

일 단위 귀속은 없어졌다. 스케줄러 틱(`CONTROL_TICK_MIN`, 기본 5분)마다 `markTick`이:

- 각 엔진의 **마지막 제안 타깃**을 실시세(데스크 호가 + 부족분은 Upbit 티커)로 마킹해
  구간 수익률을 적고, 누적 수익·**타율**(양의 구간 비율)·평균 구간 수익을 갱신한다.
  가중치는 구간마다 `w ← w × exp(η × r)`(η=8, 0.05~5로 클램프) — 하루치를 합치면
  일 단위 갱신과 같은 양이지만 반응이 5분 단위다.
- **집행된 결정**마다 `outcome`을 적는다: 집행 시점 장부 에쿼티 → 다음 집행(마감)까지의
  변화율과 마크 수. `GET /control`의 `attribution.decisions`가 결정 타율(마감된 결정 중
  양의 비율), 결정당 평균, 합계, 진행 중 결정을 낸다. 홈의 "귀속 · 5분 마크" 줄이 그것이다.

## 이력(hysteresis) — 정족수는 들어올 때만

2026-09-02 밤 장부가 매시간 SOL·ETH·BTC를 사고팔았다. 원인은 정족수 경계였다:
15분마다 오는 신호 제안의 커버리지가 바뀌면서 SOL이 "진화+신호 2명"과 "진화 1명"
사이를 오갔고, 매 집행 간격마다 들어왔다 나갔다 했다. 이제 **이미 보유 중인 시장은
제안 매니저 하나라도 지지하고 반대·거부가 없으면 유지**된다(비중은 지지자 제안과
현재 비중×1.25 중 작은 쪽). 나가는 조건은 지지 0, 센티먼트 반대, 리스크 거부뿐이다.

## 타율이 낮은 이유 (2026-09-03 분석, ₩10,000,000 초기화 후 9시간)

| 관찰 | 숫자 | 의미 |
|---|---|---|
| 집행 | 7회, 전부 매시 :32 | 집행 간격 60분에 맞춰 매시간 8~9% 회전 |
| 시간별 구간 | 21구간 중 상승 8 / 하락 12, 합계 -0.9% | 시간 단위로는 동전 던지기 — 신호의 지평(일봉 20일 모멘텀)과 판단 주기(1시간)가 안 맞는다 |
| 회전의 정체 | SOL·ETH·BTC가 들어왔다 나갔다 | 정족수 경계 flip-flop (위 이력으로 해결) |
| 유니버스 | SOPH·T·BONK·SKR·ONG — 20일 +50~220%, 일변동 8~20% | 이미 크게 오른 고변동 알트를 사는 구조. 모멘텀의 우위는 꼬리에 있지 승률에 있지 않다 |
| 비용 | 편도 0.1%, 20주문 ₩7,632 | 작지만 매시간 회전이면 하루 0.2~0.3% 드래그 |
| 표시 오류 | BONK 평단 0, SOPH +16.67% | 평단 반올림 버그 — 손익률이 엉터리로 보였다 (수정) |

결론: 낮은 "타율"의 대부분은 (1) 판단 주기가 신호 지평보다 훨씬 짧아 잡음을 거래한 것,
(2) 정족수 경계에서의 반복 매매, (3) 고변동 알트 유니버스의 본질(승률 50% 근처,
수익은 소수 큰 추세에서), (4) 평단 표시 버그다. 9시간 21구간은 통계적 결론을 낼
표본이 아니다 — 이제 5분 마크와 결정 단위 결과가 쌓이면 엔진별로 무엇이 실제로
돈을 벌었는지 분리된다.

## 귀속 (일 단위, 이전 규칙 — 참고)

매시간 `markControl`이 날짜가 바뀌었는지 보고, 바뀌었으면 각 엔진의 **마지막
제안 포트폴리오**가 그날 실제로 낸 수익률을 일봉으로 계산한다
(`getDayCandles`). 가중치는 지수가중 규칙 `w ← w × exp(η × r)` 으로 갱신되고
(η 기본 8, `quant/allocator`와 같은 규칙) 평균 1로 정규화된다. 화면의 "누적"은
그 엔진 제안을 그대로 따랐을 때의 누적 수익이다 — 집행 여부와 무관하게, 제안
자체의 성적이다.

## 사람 없이 돌아가기 — 그리고 한 손으로 멈추기

기본 상태는 **무인 운행**이다. 집행 간격 60분·최소 회전 8%가 기본이라 15분마다 오는
신호 제안까지 전부 잔거래로 집행되지는 않는다 (2026-09-02 장부가 그렇게 오염돼
₩10,000,000에서 초기화했다). 무엇이 자동인지:

| 무엇 | 어떻게 |
|---|---|
| 제안 | 오피스(로컬) `OFFICE_INTERVAL_H`, 진화 `EVOLUTION_INTERVAL_H`, 파이프라인 신호 15분(유니버스 전체) — 전부 기본 ON. 유니버스 갱신 30분 |
| 중재·집행 | 제안이 오면 즉시 중재, 오토파일럿이면 즉시 페이퍼 집행 |
| 보류 결정 | 집행 간격(`minIntervalMin`) 때문에 보류된 결정은 `CONTROL_TICK_MIN`(기본 5분) 스케줄러가 간격이 지나면 **현재 제안들로 다시 중재해 집행**한다. 사람이 승인 버튼을 누를 필요가 없다 |
| 엔진 가중치 | 매일 각 엔진의 마지막 제안이 낸 실현 수익으로 지수가중 갱신 (η=8). 손대지 않는다 |
| 만료 | TTL 지난 제안과 보류 결정은 스케줄러가 치운다 |
| 부팅 | 오토파일럿은 **매 부팅마다 `CONTROL_AUTOPILOT`(기본 true)로 돌아간다.** 화면의 승인제 토글은 그 부팅 동안만이다 — 재배포하면 다시 자동 |

화면에는 눌러야 할 것이 없다. 보류 결정 카드는 자동 모드에서 "N분 뒤 스케줄러가
집행한다"만 보여주고(간격을 기다리기 싫으면 "지금 집행 (선택)"), 승인·거부 버튼은 승인
모드로 바꿨을 때만 나온다. 집행 모드는 [자동 | 승인] 라디오, 엔진 참여는 스위치(참여/제외)로
현재 상태와 누르면 일어날 일이 같은 방향이다. `/pipeline`의 자동매매 스위치는 없앴다 —
프록시가 그 경로에 쓰기를 열지 않아 항상 실패했고, 크립토 집행은 협의회가 한다. 데스크의
신호 직접 집행 경로(`onSignal`)도 닫혔다: 신호는 제안일 뿐이다.

멈추는 손은 하나다: **`POST /control/pause`** (홈의 "자동 운행 정지"). 상태 파일에
남아 재부팅·재배포에도 유지되고, 켜져 있는 동안 모든 결정은 `blocked`로 기록된다.
`POST /control/resume`("자동 운행 재개")이 풀고 곧바로 보류 결정을 다시 중재한다.
킬 스위치(리스크)는 별개로 여전히 집행을 막는다.

상태(`GET /control`)의 `unattended`가 true면 오토파일럿 ON·정지 아님·킬스위치 아님,
즉 지금 사람 없이 집행되는 상태다.

| POST | `/api/control/engines/:id` `{enabled?, weight?}` | 세션 | 엔진 on/off, 가중 0.05~5 |
| POST | `/api/control/policy` | 세션 | 제약 수정 |
| POST | `/api/control/arbitrate` | 세션 | 지금 중재 |

WebSocket `control`(상태 전체), `control:decision`(결정 하나).

환경: `CONTROL_AUTOPILOT`(기본 true — 매 부팅의 기본값), `CONTROL_TICK_MIN`(기본 5),
`EVOLUTION_PROPOSE`(기본 true), `CRYPTO_SCANNER`·`OFFICE_LOOP`·`EVOLUTION`(전부 기본 true).

## 검증 (2026-09-02, 로컬)

부팅 직후 `signals` 엔진이 첫 제안 → 오토파일럿 집행 2건. 오토파일럿을 끄고
`POST /crypto/scanner/rotate` → 5종목 제안 → "last execution 0m ago < 30m —
held as pending" → `POST /control/approve` → 운영자 집행. 첫 실행에서 스캐너
유니버스의 알트 5종이 전부 "현재가 없음"으로 건너뛰어졌다 — 제어 평면이 데스크
관찰 종목의 가격만 알고 있었기 때문. 집행 직전 Upbit 티커로 빠진 가격을 채우는
`pricesFor`가 그 수정이다.
